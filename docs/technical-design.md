# 初步技术设计

## 1. 设计目标

本文描述满足当前产品需求所需的系统边界、关键设计原则和已经确定的技术选型。末尾的发布设计是完整初版目标；当前最小版本尚未实现其中全部能力。

设计应优先保证：

- 本机部署简单。
- 同一份服务端代码可以发布到 Windows x64、Linux x64 和 Linux ARM64。
- 路径、进程管理、关闭信号和文件系统操作保持跨平台，不依赖 Windows 专用实现。
- 网页客户端的业务核心保持平台无关，为未来增加 React Native 客户端保留复用空间，但初版不引入 React Native。
- 音乐文件和业务数据可靠持久化。
- 浏览器能够流畅播放和拖动进度。
- 转码和文件替换不会阻塞普通请求或破坏已有音频。
- 账号由服务器管理员管理，认证、稳定用户身份和业务层分离。
- 当前歌曲级设置未来可以被筛选上下文设置覆盖。

## 2. 系统边界

```text
网页客户端
  ├─ 音乐库、歌词和标签管理
  ├─ 浏览器音频播放
  ├─ 播放会话与动态权重
  └─ 本地存储恢复
          │
          │ HTTP API / 音频 Range 请求
          ▼
本地服务器
  ├─ 当前用户上下文
  ├─ 歌曲、歌词和标签业务
  ├─ 上传与文件版本管理
  ├─ 音频流
  ├─ 后台转码任务
  └─ 数据库与文件存储
```

### 2.1 客户端职责

- 展示和编辑服务器上的长期数据。
- 使用浏览器播放音频。
- 执行单曲循环和筛选结果内加权随机策略。
- 保存并恢复当前浏览器的播放会话。
- 校验服务端返回的歌曲状态，跳过不可播放歌曲。

### 2.2 服务器职责

- 提供稳定的歌曲、歌词、标签和文件版本 API。
- 保证所有业务数据归属于当前用户。
- 接收上传、识别音频、生成播放副本并保存任务状态。
- 以支持 Range 的方式提供音频内容。
- 安全地替换和删除文件。
- 在服务重启后恢复长期数据和未完成任务的可诊断状态。

## 3. 建议的数据概念

这里列出概念关系，不作为最终数据库表定义。

### 3.1 User

- `id`
- `displayName`
- `createdAt`
- 未来凭证和状态字段

初版启动时确保存在一个默认用户。

### 3.2 Track

- `id`
- `ownerUserId`
- 从当前音频文件读取的元数据；显示名称和歌手允许用户覆盖，其他字段只读
- `fileName` 保存当前原始上传文件名，`uploadedAt` 映射首次创建歌曲的 `created_at`；历史数据用迁移时的标题回填文件名
- `custom_title`、`custom_artist` 记录用户是否修改过显示名称和歌手，替换音频时保留已自定义字段
- `baseRandomWeight`，默认 `1.0`
- `playbackStartSeconds`，默认 `0`
- `playbackEndSeconds`，可为空，表示音频结尾
- `volumeRatio`，默认 `0.8`
- `activeAudioVersionId`
- `original_content_type` 保存探测出的原始容器 MIME，不以扩展名判断；`playback_index_version` 标记兼容副本已验证的索引版本
- `deletedAt`，为空表示正常歌曲；有值表示位于回收站
- `purgeEligibleAt`，不得早于 `deletedAt + 72 小时`
- `createdAt`、`updatedAt`

### 3.3 AudioVersion

完整初版的数据模型为：

- `id`
- `trackId`
- 原始文件引用
- 播放副本引用
- 文件校验值
- 原始格式、编码和时长
- 原始文件与播放副本的字节数
- 处理状态和错误信息
- 版本创建时间

歌曲与音频版本分离后，替换文件可以先创建候选版本，成功后再更新歌曲的活动版本引用。

当前第一阶段采用满足同一行为约束的简化落地：`tracks` 保存当前原始文件、播放文件和单调递增的 `audio_version`；新文件在数据库外准备并验证完成后，通过一个事务替换这些字段。旧文件写入持久化的 `pending_file_deletions` 表，实际删除前继续计入配额。由于当前不保留历史版本，这一实现不向用户暴露旧文件，也不改变替换的原子性和失败回退语义。当前上传与替换任务由独立的 `upload_jobs` 表持久化；引入校验值或版本历史时，再迁移到独立 `AudioVersion` 表。

### 3.4 Lyrics

- `id`
- `trackId`
- 类型：纯文本或 LRC
- 原始文本
- `updatedAt`

服务器仍把歌词作为原始文本保存。平台无关的 TypeScript 共享包负责解析常见 LRC 行时间戳并计算当前歌词行；Web 适配层负责随播放位置高亮、滚动和点击跳转。普通文本按行展示，不在服务器保存解析后的派生结构。同一时间戳合并为一个 `LyricLine`，保留首行 `text`，其余去重后存于可选 `secondaryTexts`；Web 将附加行以较小字号展示，点击整组跳至同一时间。

解析规则严格按原时间戳分组，不根据语言、文字类型或相邻时间结构推断原文、译文和配对关系，也不提供推测建议；不确定的主次关系由用户指定组内第一行或最后一行为主行。用户可选择独立显示，此时同时刻各行均高亮，只选一个滚动锚点。显示选项仅影响排版，不改变时间或服务器中的歌词文本。

Web 播放视图以当前音频位置加 0.3 秒查询活动歌词行，提前触发高亮与平滑滚动以补偿动画耗时。该提前量只用于播放视图，叠加于解析器已应用的 LRC offset，不改变解析结果、设置预览、音频进度或点击歌词的跳转目标；普通文本歌词不受影响。

Web 使用受 `100dvh` 约束的播放工作区：宽度大于 1100px 时歌曲列表与歌词并排，其他尺寸点击播放器的封面、歌名、歌手名所在完整信息区双向切换列表与歌词，按钮可访问名称随当前目标变化，不显示独立视图按钮。回收站中点击进入歌词，应用标签组仍返回列表；仅改变视图状态，不重置标签开关或播放会话。列表和歌词各自保留独立滚动容器。歌词居中使用容器自身的 `scrollTo`，不调用会滚动祖先页面的 `scrollIntoView`；视图切换和容器尺寸变化时重新定位活动行。切换视图不卸载列表和歌词，不改变播放状态、进度或歌曲设置；播放器独立固定在底部，回收站单独滚动。

`[kana:…]` 由平台无关解析器转换为可选 `ruby` / `secondaryRuby` 片段，Web 通过原生 `ruby/rt/rp` 元素显示；不新增依赖、存储字段或开关。支持单个数字 1–9 表示后续读音覆盖的汉字数量、空读音占位，以及可去掉时间参数后静态展示的假名片段；格式参考 [公开解析测试](https://github.com/SPlayer-Dev/lyric-kit/blob/main/tests/kana.spec.ts)。按原始物理行顺序消费基础槽位：统一表意文字、々、〇、〆 各占一个，连续半角或全角数字串作为整体占一个；元数据不消费槽位，多时间戳重复行共用该物理行注音。先对全部正文严格对齐；数量或边界不符时，分别尝试同时间组的第一行、最后一行组成的候选，按物理行去重并恢复源行序。原始 0 秒的多行组可用唯一的 `[ti:…]` 标题元数据核对标题行，允许其括号说明及艺术家后缀；只有唯一行匹配标题前缀时才固定该标题行，不让同组网站提示占用标题槽位。其他时间组不使用标题规则；冲突标题元数据不自动选行。每个候选优先匹配完整序列，仍不匹配时只允许再匹配截至最后一个多行组的完整序列，末尾单独行保留但不注音。只有一套候选能完整对应时，注音绑定到这套候选的文字，主行切换仅改变显示位置；两套都能对应时才按用户主行选择区分，独立行模式遇到多解则保持普通显示。不得跳过中间行或 token，也不根据语言选择原文。所有候选都要求槽位总数量完全相等，多槽位读音只能覆盖同一行连续的基础 token；冲突标签、异常读音或无法匹配时回退普通文本。注音在时间排序和分组前绑定文本，主行切换时同时交换注音片段，译文或附加行也保留自己的注音。原始歌词及时间不修改，kana 元数据不显示为正文。

迁移 `007_lyrics_display` 引入歌词显示设置；后续迁移 `008_remove_lyrics_inference` 将历史 `end-timed` 选择重置为 `timestamp`，保留歌词、主行位置及其他歌曲设置，不增加音频版本；回滚不猜测恢复已撤销的选择。API 只接受 `lyricsLayout=timestamp/separate` 与 `lyricsPrimaryLine=first/last`，非法值（含已撤销的 `end-timed`）拒绝且不修改任何设置，省略或 null 保留原选择。选项属于歌曲，保存在服务器，替换音频、删除恢复不重置。

整体偏移直接在歌词文本内以 LRC `[offset:毫秒]` 手动编辑，不提供独立输入框，不新增 API 字段或数据库列。正数提前、负数延后（参考 [paroles 的 offset 说明](https://github.com/Clarkkkk/paroles)），解析器读取最后一个可安全表示的整数毫秒标签，无效或溢出标签忽略。共享解析器保留偏移后的负时间，不把不同负时间合并到 0 秒；音频为 0 秒时选择最近的非正时间行，Web 点击跳转限制到 0 秒，预览保留负号并显示毫秒精度。

歌曲保存统一通过 Store.UpdateTrack 补齐标签：非空歌词已有有效整数 offset（大小写不敏感，可带正负号，范围为 JavaScript 安全整数毫秒）时逐字保留；缺少有效标签时，在 BOM 之后按原文件第一处换行风格补 `[offset:0]`，不改写其他内容。空字符串、纯空白或仅 BOM/空白不补标签，以保留清空歌词的行为。归一化与歌曲设置写入在同一条更新语句中完成，验证失败不得修改歌词；返回的歌曲包含补齐后的文本。既有记录不主动迁移，只在保存时补齐。该逻辑幂等，重复保存不累加标签；手动编辑草稿仅在用户确认保存后生效，取消不影响服务器或当前播放。

歌词候选搜索由 Go 服务端调用 LRCLIB，浏览器不直接依赖外部服务。服务端根据歌曲元数据或文件名中的“艺术家 - 标题”形式生成简易查询，按标题、艺术家、时长和同步歌词可用性排序。当带歌手搜索得到的可用、去重候选少于 3 个时，追加一次不带歌手的歌名搜索，合并并沿用原歌手信息评分、去重后取前 8 个；没有歌手时不重复查询。补充查询失败时保留已有候选，没有已有候选则返回错误。响应通过 `expandedSearch` 表明成功进行了补充查询。搜索只返回候选，不持久化；用户选择候选并通过现有歌曲更新接口保存后才修改歌词。外部服务超时、限流或不可用时不得影响本地音乐播放。

网页新上传首先通过 `POST /api/uploads/check` 接收文件并用 FFprobe 仅读取标题标签（无标签回退文件名），不解码时长或转码。内部以 `kind=preflight` 记录配额与候选路径，完整接收后保持 queued，以 `pending_candidate` 保存标题和匹配的目标 ID；不进入 `GET /api/jobs`，工作器跳过。客户端显示独立检查进度，同名弹窗先确认；通过 `POST /api/jobs/{jobID}/resolve` 的 `overwrite=true` 与 `requestKey` 将候选发布为正式 upload 任务，之后才显示列表、增加会话角标并开始处理；取消仅清理预检查文件，不计数。确认事务重新核对目标同名关系，目标被删除、改名或出现新的同名记录则拒绝启动，客户端清理候选并提示重新选择，不重复上传文件。预检查关闭或刷新后不恢复弹窗，启动恢复会清理所有未确认 preflight，维护清理达到一小时的 queued preflight，清理失败保留配额并重试。复用已有 kind、pending_candidate 和任务状态，不新增数据库字段。

上传任务激活歌曲的事务内仍作为并发和旧客户端的兜底，按 `strings.EqualFold(strings.TrimSpace(title), …)` 检查当前用户的未删除同名歌曲，不以歌手或文件名区分；没有标题标签时沿用文件名回退。迁移 `009_upload_conflicts` 添加 `pending_candidate`，同名任务将完整候选元数据持久化，保持 `queued` 并标记 `requiresConfirmation`，工作器跳过此类任务；候选文件与配额预留保留，刷新、重启无需重新上传或转码。`POST /api/jobs/{jobID}/resolve` 接收 `overwrite` 布尔值：确认通过原子替换流程激活候选并登记旧文件清理，取消将任务置为 failed（原因“已取消”）并清理候选，清理中断沿用失败任务恢复。等待选择时客户端停止轮询；确认失败保留候选供重试或取消。事务检查任务状态、目标存活及同名关系，防止重复提交或目标改名后误覆盖；同名并发上传的激活串行检查。历史重复记录取最早上传的一首，不主动合并；回收站不参与重复判断。

### 3.5 Tag / TrackTag

`tags` 归属用户，名称以 SQLite NOCASE 在该用户内唯一；允许任意字符，去除首尾空白后以半角位计数，总计 1–4 位（W/F 宽字符及 Emoji 计 2，其余计 1；组合附加符不另计，常见 Emoji 序列整体计宽）；保留“无”。`track_tags` 为歌曲与标签的多对多关系，标签、歌曲永久清理均级联移除引用。歌曲软删除不移除标签，恢复后继续生效。系统筛选 ID `_untagged` 不写入标签表、不能赋给歌曲，界面显示“无”。

宽度校验使用固定的 Unicode 17.0.0 数据：[EastAsianWidth](https://www.unicode.org/Public/17.0.0/ucd/EastAsianWidth.txt)、[emoji-data](https://www.unicode.org/Public/17.0.0/ucd/emoji/emoji-data.txt) 和 DerivedGeneralCategory。`scripts/generate-tag-width-data.py` 生成 Go 与 TypeScript 的相同范围表，无运行时下载或字体测量；两端共同读取 `api/tag-width-cases.json` 验证全半角、组合符、旗帜、肤色、键帽和 ZWJ 序列。标签组仍按 1–4 个 Unicode 字符限制，不使用此宽度规则。

### 3.6 TagGroup / TagGroupTag

`tag_groups` 保存用户标签组名称、默认标志及无标签开关；`tag_group_tags` 保存普通标签组中开启的真实标签引用，未引用即关闭。默认标签组在读取时动态包含全部标签和 `_untagged`，不保存静态快照。新建与编辑名称限制 1–4 个 Unicode 字符；已有名称不改写，客户端缩略并保留完整提示，系统默认标签组显示“全部”；默认标签组不可更改，普通标签组允许全关闭。创建账号与新建默认标签组在同一事务内完成。

`GET /api/library` 一次返回当前用户全部未删除歌曲（含 `tagIds`）、真实标签和标签组，音乐库不再从默认歌单推导。`POST/PATCH/DELETE /api/tags`、`POST/PUT/DELETE /api/tag-groups` 管理标签及标签组；`PATCH /api/track-tags` 在单个事务内验证歌曲及标签归属并更新。Web 批量编辑仅使用 add/remove；添加弹窗可创建或选中同名已有标签，刷新音乐库后自动勾选，筛选选择不因默认全开模式新增标签而清空或关闭弹窗。歌曲行展示小标签，单曲设置保存不发送 `tagIds`，防止旧编辑快照覆盖标签关系。服务端 replace 及原 PATCH 的可选 `tagIds` 仅保留旧客户端兼容。歌词、封面、音频替换保持既有接口。

迁移 016 建表，017 在单一事务内将旧普通歌单转换成标签和同名标签组，连同软删除歌曲的关系一起转换；过长或重名的旧名称使用确定性的短标签，完整名称保留在标签组上。旧表及原 API 作为上传历史与旧客户端的兼容层保留，不再供新界面筛选、排序、随机播放或删除语义使用；未来清理必须另做迁移，不在验收前删除源关系。新上传不继承当前筛选标签，旧客户端上传中保存的歌单字段不转成标签。

Web 使用平台中立 `filterTracks` 以 OR 组合开关，只生成去重的可见列表和随机候选；当前播放对象从全部歌曲查找，筛选变化不卸载或重新定位音频。旧 `playlistID` 保留为播放快照兼容字段，不代表新界面的播放范围。当前 `tagSelection` 随用户隔离的播放会话保存，省略表示全开（含新标签），空数组表示全关；普通标签组应用为显式数组，默认标签组应用为省略。服务端变更后移除失效标签 ID，随机衰减仅在歌曲真实删除时清理，按当前候选数量恢复。

宽窄屏共用 `TagPanel`，直接展示标签开关和下沿标签组页签，顶部一个编辑按钮统一切换编辑模式。标签组加号按完整开关集合匹配判断，仅在无匹配或编辑时显示，仅无匹配时高亮，默认组按动态 allTagIDs 判断；新建草稿不随匹配状态变化而卸载。标签编辑区只允许已有标签改名和删除，创建仅通过歌曲批量添加弹窗完成；标签组仍可通过加号创建。两类名称复用 Web `InlineNameEditor`，输入自动聚焦选中，支持 Enter/Esc、组合输入保护、SVG 保存/取消/删除；标签组草稿由 TagPanel 持有；编辑已有组时将 TagFilter 临时切为该组开关编辑器，无双击独选与标签改名，不增加第二套开关。下方标记正在编辑的组，保存或取消后恢复标签行。编辑仅更新草稿，不调用播放筛选变更；提交时禁用草稿开关与退出按钮，失败保留名称及开关草稿。编辑不会调用筛选或应用接口，默认标签组与“无”禁止编辑。取消标签组弹窗及 Portal，响应式变化不卸载编辑器；窄屏批量栏替换两行区域时用 visibility 保留高度。窄屏标签区使用两行 Grid：第一行标签及编辑按钮，第二行左侧标签组、右侧独立竖向三点按钮，按钮与编辑入口统一尺寸及描边；标签组换行不挤占按钮列。音乐库菜单继续折叠展示上传、排序及账号等工具，不卸载上传任务，支持外部点击、Esc 关闭及返回焦点。

### 3.7 TranscodeJob

当前实现使用 `upload_jobs`：任务记录文件名、目标歌曲（替换时）、源文件路径、候选输出路径、空间预留、状态、错误及创建/更新时间。状态依次为 `receiving → queued → processing → succeeded`，失败进入 `failed`；成功时记录歌曲 ID。路径由服务器生成的任务 ID 决定，不使用用户文件名作为存储路径。

- `id`
- `audioVersionId`
- 状态、进度和错误信息
- 尝试次数
- 创建、开始和完成时间

任务记录应与具体后台执行方式解耦。

### 3.8 StorageQuota

- 固定的服务实例级配额 ID
- `limitBytes`，初版默认 `10 × 1024³`
- 已提交占用字节数
- 为并发上传、转码或替换保留的字节数
- 版本号或其他并发控制字段

初版所有账号共享这一服务实例级配额。所有会产生文件的流程必须先通过原子更新申请空间，完成后将预留转换为实际占用，失败后释放预留。回收站文件在永久清理前仍计入占用。

## 4. 最终播放参数解析

播放器不应在各处直接拼装歌曲字段，应通过统一解析逻辑获得最终参数。预留的优先级为：

```text
歌曲默认参数
  → 可选的筛选上下文覆盖
  → 可选的本次播放临时覆盖
  → 最终播放参数
```

初版只有第一层产生实际值，后两层为空。该边界能够避免未来加入上下文配置时重写播放器。

## 5. 加权随机算法

### 5.1 会话状态

客户端为当前播放会话维护：

- 播放会话 ID
- 当前歌曲 ID
- 每首最近播放过的歌曲距离上次播放的切歌次数
- 完整保留每首歌的实际切歌计数，不再截断到 `3`；线性恢复周期取 `max(1, 当前筛选可播放歌曲数 / 2)`，不向整数取整

从未在当前会话播放过的歌曲视为已经完全恢复。

### 5.2 选择下一首

1. 从当前标签筛选结果取得状态为可播放的歌曲。
2. 如果没有候选歌曲，停止并提示。
3. 如果只有一首候选歌曲，选择该歌曲。
4. 如果有多首候选歌曲，排除当前歌曲。
5. 从剩余歌曲中优先只保留当前会话步数未记录或至少为 `2` 的歌曲，避开最近两首，防止 A → B → A；若没有这样的候选（如两首歌交替），放宽到步骤 4 的候选。该过滤必须先于权重计算及全零权重回退，回退不得重新引入已排除的歌曲。
6. 根据切歌次数及整个当前筛选结果的可播放歌曲数，按 `基础权重 × min(1, 切歌次数 / max(1, 歌曲数 / 2))` 计算保留歌曲的有效权重，按比例抽取下一首；有效权重全不可用时，仅在保留的候选中使用基础权重。
7. 成功切换后，推进其他曾播放歌曲的恢复步数，并将新歌曲的步数重置为 `0`。
8. 将更新后的会话状态写入本地存储。

实现时应使用无偏的累计权重抽样，并防御非法数值、浮点溢出和有效权重总和异常。基础权重只接受大于 `0` 的有限值。

避让复用已有 `RecoveryState` 步数，无需增加会话存储字段，刷新后按已持久化状态继续避让。手动点歌绕过随机候选过滤；如果目标已经是步数为 `0` 的当前歌曲，则不推进恢复步数，防止重复点选绕过避让。

恢复计数仅以 JavaScript 最大安全整数为上限，不在达到完整权重后截断，保证筛选范围扩大时仍能按实际计数重算；候选增删立即影响分母，但不改变候选避让规则。沿用现有会话字段，旧会话曾截断到 3 的历史计数无法重建，读取后按原数值继续累计，无需清空会话或迁移数据库。

## 6. 音频上传与转码流程

```text
接收上传
  → 检查并预留可用空间
  → 保存到候选位置，同时持续校验配额
  → 计算校验值并探测格式
  → 读取时长和元数据
  → 判断是否为已验证可直接播放的标准 MP3
      ├─ 是：登记为播放版本
      └─ 否：创建 MP3 转码任务
  → 验证播放版本
  → 激活音频版本
  → 新上传歌曲进入音乐库，默认无标签
```

HTTP 接口当前约定：网页通过上述预检查与确认接口提交新上传；保留兼容接口 `POST /api/tracks` 和 `PUT /api/tracks/{trackID}/audio` 每请求接收一个文件，客户端可并发发起多请求；完整接收并落盘后返回 `202` 和任务信息，不等待探测/转码。`GET /api/jobs` 返回当前用户的所有活动任务和最近 100 条完成/失败任务；客户端仅在本地正在上传或服务器有接收、排队、处理中的任务时每 1.5 秒轮询；全部完成或失败后停止定时查询，新上传时恢复，页面重新打开或窗口重新获得焦点时仍可刷新状态。接收中刷新会中断该次传输，已完整接收的后台任务不受影响；暂不支持断点续传或手动重试转码，失败文件需重新选择上传。

关键原则：

- 用户提供的文件名不能直接决定服务器存储路径。
- 上传和转码中的文件与已经激活的文件分开存放。
- 数据库只在文件已经安全写入后引用文件。
- 对外提供音频时使用稳定 ID，而不是暴露磁盘路径。
- 转码任务不得长时间占用普通 HTTP 请求。
- 服务器应能够识别并处理数据库记录与文件状态不一致的情况。
- 初版不设置单文件大小或任务并发数量上限，但所有并发流程仍受总空间配额约束。
- 无法预先获得文件大小时，应在流式写入过程中分段申请空间；申请失败后立即中止并清理候选文件。
- 上传通常每次原子预留 4 MiB，在预留额度内连续写入，不再逐 multipart 小块更新 SQLite；接近配额上限时允许按实际剩余额度预留，只要足够覆盖下一次写入。文件同步落盘后，在同一次条件更新中将预留结算为实际接收字节并转为排队状态；中断或写入失败沿用候选文件清理及预留回收机制。配额总和包含歌曲、待删除文件及所有任务预留。转码前按源时长 × 40,000 字节/秒 + 64 KiB 保守预留输出空间，FFmpeg 通过标准输出流写入受控 writer；超出预估时先原子扩容预留，再允许继续写入。完成后同步落盘并探测验证，在激活事务中按实际大小结算。

### 6.1 统一兼容副本参数

- 文件扩展名：`.mp3`
- MIME 类型：`audio/mpeg`
- 编码器：LAME MP3
- 码率模式：VBR
- 质量等级：`q=2`，通常约 190 kbps
- 声道：保留单声道；多于双声道时下混为双声道
- 采样率：保留不高于 48 kHz 的常见采样率；更高采样率降至 48 kHz

选择 MP3 是为了以一个播放副本覆盖尽可能广的浏览器范围。MDN 将 MP3 描述为所有主流浏览器支持的格式，并建议音乐场景尽量使用至少约 192 kbps 的码率：

- [Web audio codec guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Audio_codecs)
- [Media container formats](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/Containers)

### 6.2 原文件优先与时间索引

API 同时返回 `originalAudioUrl`、`originalContentType` 与兼容副本的 `audioUrl`。`/api/tracks/{id}/audio?source=original` 提供原文件，使用探测容器得到的 MIME 并支持 Range；默认音频端点仍提供兼容副本。两者均验证歌曲归属与未删除状态，并携带音频版本标识。

裸 ADTS AAC 不返回可优先选择的 `originalAudioUrl`，避免浏览器按码率估算时长造成进度和拖动异常；原文件仍保留且原始音频端点可用。M4A/MP4 中的 AAC 不受此限制。

Web 音频适配器通过 `canPlayType` 优先选择原文件，不支持时直接使用 MP3；原文件解码失败后最多回退一次，待新来源的元数据就绪后恢复当前位置，保持音量和播放意图。自动播放权限错误不触发格式回退。未设置播放终点时依赖音频原生 `ended` 事件；显式终点才由播放策略截断。

裸 ADTS AAC 的 `ffprobe` 时长可能来自码率估算。探测到 `format_name=aac` 时，额外通过 FFmpeg 完整解码到 null 输出，以最终 `out_time_us` 确定时长；解码失败、取消或缺少有效时长时不得回退到估算值。其他容器保持常规探测流程。

VBR MP3 直接输出到 `pipe:1` 无法回写 Xing 索引。当前先通过受配额控制的 writer 生成 `.stream` 中间文件，再原子预留中间文件大小 + 4 KiB 的重封装空间，将音频包复制到可回写的最终 MP3，补写 Xing/TOC，不二次编码。重封装不复制源元数据或图片，并限制输出长度，为最后一个 MP3 数据包和索引留余量。文件同步落盘后，探测时长与原文件误差必须不超过 150 毫秒；然后清理中间文件，在激活事务中结算最终占用。崩溃或失败时按任务记录清理两份候选文件，清理失败前继续保留预留额度。

迁移 `005_original_playback` 为历史记录补充格式与索引状态。启动恢复完成后及每小时维护时，探测旧记录的原文件 MIME，增加音频版本以作废旧时间轴的会话进度，并为未验证的兼容副本登记 `kind=repair` 后台任务；同一歌曲只允许一个活动修复任务。修复作为内部维护静默执行，不在前端上传任务列表展示，也不计入该列表数量或影响展开状态；任务状态仍可用于更新音频版本和容量缓存。旧副本作为只读输入，候选副本另行预留空间；成功时在同一事务中切换副本、增加音频版本、调整占用、标记索引版本并登记旧副本清理。失败或中断时只清理候选输出，绝不删除仍在使用的修复输入。重启恢复删除未完成输出、释放其预留并重新排队；空间不足时保持旧文件可用，后续维护可重试。修复不修改歌词、歌曲名称、歌手、标签关系或播放设置。

迁移 `006_accurate_duration` 增加 `duration_probe_version`。新上传及替换音频写入已校准版本；历史裸 AAC（包含已知 MIME 或已修复索引的记录）在启动及维护时重新探测一次，并在事务更新中校准时长、增加音频版本。起点超出新时长时恢复完整播放；仅终点越界时收至新结尾，其他设置保留。更新要求原路径和音频版本仍与探测快照一致，避免覆盖并发替换；失败保留未校准状态以供下次重试。校准先于索引修复排队，旧的失败修复可自动重新排队；再次重启不重复校准。

## 7. 音频替换流程

```text
为歌曲上传替换文件
  → 为原文件和预计播放副本预留空间
  → 持久化上传/替换任务并创建非活动候选文件（完整初版为 AudioVersion 记录）
  → 探测并按需转码
  → 验证新播放版本
  → 在事务中切换当前文件引用并递增音频版本号（完整初版切换 activeAudioVersionId）
  → 立即清理旧音频版本
```

切换活动版本后，客户端通过音频版本 ID 发现本地保存的旧播放进度已经失效。

旧版本不设置保留期。活动版本切换成功后立即尝试删除旧原始文件、旧播放副本和旧版本记录，并扣减空间占用。

文件删除不应放在数据库切换事务内部长期阻塞。若文件被占用或删除失败，应将旧版本标记为待重试清理；新版本仍保持活动状态，旧版本不再对外提供播放。待重试文件在实际删除前继续计入已用容量。

## 8. 删除与回收站

### 8.1 标签关系与歌曲删除

标签和标签组仅负责组织歌曲；删除标签及标签组不删除歌曲，标签外键级联移除相关关系。工具栏删除始终调用音乐库级歌曲软删除接口，确认后逐曲执行，失败项保留选择以便重试；不再区分“从歌单移除”和“删除歌曲”。

### 8.2 软删除与恢复

软删除歌曲时设置 `deletedAt` 和 `purgeEligibleAt`，但不立即删除音频、歌词和标签关系。所有正常业务查询统一过滤已删除歌曲。

恢复时清除删除标记，原有标签关系继续生效；已被删除的标签不重建。

### 8.3 延迟永久清理

永久清理器只处理 `purgeEligibleAt <= 当前时间` 的歌曲。建议挂在以下触发点：

- 服务器启动完成后
- 成功执行删除操作后
- 上传或替换任务完成后
- 可选的低频后台维护计时器

清理器应是幂等、可重入且失败可重试的。触发器只负责发起一次尽力清理，不应阻塞用户操作。没有触发时，歌曲可以在回收站中保留超过 72 小时。

永久清理建议分为“领取清理任务、删除文件、删除或封存数据库记录、扣减空间占用”几个可恢复步骤。任何情况下都不得在 `purgeEligibleAt` 之前删除文件。

初版不提供用户主动永久删除或清空回收站的接口。

## 9. 音频传输

- 音频端点必须支持 HTTP Range 请求。
- 应正确返回内容长度、媒体类型、范围响应和不可满足范围响应。
- 音频 URL 应包含稳定的版本标识，避免替换后浏览器继续使用旧缓存。
- 服务器应避免一次性将完整大文件读入内存。
- 只有归属于当前用户且状态可播放的音频版本可以访问。

播放快捷键在 Web 适配层监听键盘事件，调用现有播放、切歌、跳转和主音量操作；不向共享包引入 DOM 事件。回调随当前状态更新，监听器只注册一次并在卸载时移除。忽略输入控件、可编辑区域、弹窗、输入法组合、已被局部控件消费的事件及浏览器修饰键组合；原生按钮空格操作优先。方向键允许长按，播放切换、静音和切歌忽略重复按键。帮助使用原生 modal dialog，阻断背景快捷键并支持 Esc 关闭及焦点恢复。

Web 的 Media Session 适配器使用 `navigator.mediaSession` 和 `MediaMetadata` 发布当前歌曲信息，封面沿用受保护的同源版本化 URL，不增加公开媒体接口。系统 play/pause/stop 调用现有播放状态操作（stop 暂停并保留进度），nexttrack 调用当前筛选结果的随机策略，previoustrack 不注册；seekto 和快进快退读取实时音频位置并限定单曲播放区间。回调引用随状态更新，避免重复注册或使用旧筛选结果。音频进度、元数据就绪、跳转、速率及播放事件更新系统原文件时间轴和播放状态，不额外轮询、加载音频或修改速率；优先采用浏览器实际时长，未就绪时使用服务器时长，仅提交有限且有效的位置参数。逐项容忍缺失或不支持的 API；无当前歌曲及卸载时解除动作和音频监听并清空元数据、进度及状态。所有浏览器类型留在 Web 层。

Web 画中画歌词通过 Document Picture-in-Picture API 由用户点击打开，能力检测与 requestWindow 位于 Web 适配层。React Portal 将当前与下一歌词时间组和控制按钮渲染到同源画中画文档，使用独立样式；保留固定文档名称但不尝试将歌名写入浏览器来源标题栏，复用 TrackCover 显示模糊背景及失败回退，歌词使用完整内容区居中且不为按钮预留底部空间，按钮绝对定位并覆盖在底部，使用半透明深色圆形 SVG 图标；通过 hover 和键盘输入模式下的 focus-visible 显示，指针移动、按下或移出时退出键盘显示模式，保留按钮焦点但不让其阻止鼠标移出后隐藏；hover:none 下保持可见，不引起歌词布局移动，不移动或卸载主界面歌词，也不创建音频实例。继续使用共享解析器、LyricText 和统一的 300 毫秒动画提前量；独立行模式同时间的多行一起显示。相邻歌词时间组通过 Web Animations API 根据前后布局位置做 300 毫秒上移过渡，退出行复制为不可交互且对辅助技术隐藏的临时层；动画完成、后续切换和组件卸载时清理。仅在同一歌曲、同一解析结果及窗口尺寸不变时对相邻组做动画，跨句跳转和减少动态效果时直接定位，进度更新不重复启动动画。窗口关闭通过 pagehide 同步入口状态，组件卸载关闭窗口，异步打开结束时检查组件仍挂载；取消播放或切歌不重开窗口。无需后端接口、存储字段或依赖变更。

## 10. 客户端本地状态

取消任务仍以 failed / “已取消” 作为内部清理标记，不新增状态枚举；API 与客户端均不将其展示为历史任务。清理候选文件成功并将预留归零后，通过受当前用户、failed、取消标记和零预留约束的删除语句移除 upload_jobs 记录；真实失败和成功任务不在该规则内。维护任务也重试零预留的历史取消记录，先确认文件清理再删除；失败重启恢复沿用同一流程。客户端取消成功时丢弃对应本地进度，避免服务端记录删除后重新显示为“上传中”。

Web 适配层的 `music-upload-session-v1` 保留随机会话标识与请求序号，用于组成 `X-Upload-Key`、幂等提交及关联本地与服务器任务；仅确认发布正式任务或明确替换时递增，预检查和取消不递增。序号不再用于展示上传入口的数量。浏览器存储不可用时在内存保留，不阻止上传，不保存文件或传输进度。

上传进度面板只展示进行中、待确认、未关闭的失败，以及当前页面新完成的任务；初次加载的成功历史不进入面板。入口数字为当前未完成任务数，不使用会话累计上传数。文件接收和任务轮询组件在应用中保持挂载，通过 Portal 将宽屏入口放到左下角“上传音乐”旁，任务列表向上展开；窄屏入口仍在列表工具区靠右；窄屏歌词或回收站改用播放器上方的临时浮动入口。切换标签组或视图不丢失本地检查、待确认和失败状态。关闭失败提示仅作用于当前页面，不删除服务器任务；数据库记录继续用于恢复。成功记录及入口保留到页面刷新；上传中不自动展开，手动展开后任务更新不将其收起，失败或待确认时仍可自动展开；终态不继续轮询；内部修复和封面任务仍按原策略静默刷新歌曲与容量。

播放会话使用 `sessionStorage`，键为 `music-player-session-v2:<编码后的用户ID>`。快照为 `{version: 2, userId, sessionId, savedAt, state}`；`savedAt` 为最后一次实际写入的 Unix 毫秒时间，`sessionId` 在新会话时随机生成，刷新沿用。只保存播放字段，不序列化 Zustand 方法或歌曲数据。

网页启动先请求不可缓存的 `GET /api/current-user`，身份来自服务端当前用户上下文，忽略客户端传入的身份；确认身份后才读取对应会话并挂载播放器。该接口的 `isDefault` 仅用于允许默认账号迁移旧版、未分用户的 `music-player-session-v1`，迁移后删除旧键；其他用户不得继承旧记录。不同用户的键及快照内用户 ID 必须匹配，切换用户先提交旧用户的待存进度，再重置内存状态和订阅。

进度在内存持续更新，使用 2 秒尾沿节流，每个窗口只序列化并保存最新快照。暂停、切歌、切换标签开关、模式及主音量变化、手动跳转、恢复校验修正立即保存并取消待执行计时器。`pagehide`、`beforeunload` 和页面隐藏时采样音频当前位置并立即提交，减少刷新、关闭或手机切后台时的进度损失。连续更新不得反复延后写入时间。存储读取、解析、写入失败或不支持的数据版本均安全回退，不阻止播放。

切回网页或窗口重新获得焦点时，不主动请求当前用户；后续受保护请求返回 401 时统一处理登录失效。其他标签页切换账号后，本页不主动同步身份，刷新时重新确认。

初版不实现标签页间锁、广播或播放状态协调；每个标签页独立运行是允许的。关闭标签页后不保证恢复该播放会话。

恢复流程：

1. 读取并迁移或拒绝不支持的本地结构版本。
2. 向服务器验证用户、标签、歌曲和音频版本。
3. 清除已从整个音乐库移除的随机状态条目，以及负数、非整数、非有限值等非法状态；此校验也在服务器音乐库数据每次刷新后执行。
4. 将进度限制在当前歌曲播放区间内；音频版本变化或进度已到终点时从当前片段起点恢复。歌曲失效则清空当前歌曲、版本、进度并暂停；已删除标签从开关中移除，标签筛选不清空仍属于音乐库的随机状态。
5. 恢复界面状态，但遵守浏览器自动播放限制；需要用户操作时保持暂停并提示继续播放。

## 11. 当前用户边界

业务服务只依赖“当前用户上下文”，不直接依赖默认用户常量。

请求进入服务器后，由登录会话解析当前用户，歌曲、歌词、标签和标签组服务按当前用户过滤数据；默认账号仅用于承接升级前的现有音乐库。

当前实现通过 `currentuser.WithID/ID/Require` 使用私有键携带请求身份。HTTP 中间件从登录会话取得用户，也允许通过服务端 `API.ResolveUser` 接入受信任认证适配器；没有适配器时必须校验会话，不再匿名返回引导账号。客户端传入的用户 ID 参数、Header 或请求体不会选择用户，解析失败或空身份返回 401。用户资源的数据访问必须显式传递带身份的 context，缺失时报错；默认用户常量只用于初始化和兼容旧数据。SQL 以当前身份限定歌曲、标签、标签组、任务及关联对象；默认标签组按所属用户和 is_default 查询，旧歌单仅供兼容层使用。

迁移 `015_account_sessions` 增加按用户及凭据类型存储的 `user_credentials` 与 `login_sessions`，不改变任何业务数据归属。账号作为唯一登录秘密，使用随机 16 字节盐、PBKDF2-HMAC-SHA256（600000 次、32 字节）保存校验值，逐项校验且拒绝重复凭据；稳定用户 ID、显示名和凭据分离，认证类型独立以预留密码等方式。会话使用 32 字节随机令牌，数据库仅保存 SHA-256 摘要及 30 天过期时间。创建会话同时检查本次校验的凭据版本，防止管理员重置期间用旧校验结果生成新会话；重置和停用以事务撤销该用户全部会话。创建重复账号时整个用户及默认标签组事务回滚，停用不删除音乐库。

`POST /api/auth/login` 接受 `{account}`，成功设置 HttpOnly、SameSite=Strict、Path=/ 的主机级 Cookie；`POST /api/auth/logout` 撤销会话并清除 Cookie。HTTPS 直连或来自回环代理且 `X-Forwarded-Proto=https` 时加 Secure；不信任公网请求的代理身份头。静态网页、登录、退出和健康检查不依赖已登录身份，其他已注册 API、原音频、兼容副本及封面统一受保护。登录及私有元数据禁止缓存；音频和封面允许私有缓存但每次使用需重新校验。写请求校验 Origin 与请求来源，拒绝跨站操作；登录每分钟全实例最多 20 次尝试、同时最多 2 次校验，超限返回 429。没有客户端注册或管理员 HTTP 接口。

管理员使用同一服务程序的 `account add/reset/disable/list` 子命令，复用配置解析及版本化数据库迁移，但不启动 HTTP、FFmpeg 或后台任务；必须使用与服务相同的数据目录。`--id default-user` 为现有库配置登录，其他 ID 添加独立用户。默认生成 32 字节随机账号并仅向命令标准输出显示一次，`--account-stdin` 从标准输入读取指定账号且不回显，列表从不返回凭据。网页只在身份确认并初始化该用户播放持久化后挂载播放器，账号框普通文本可见；登录失败不会挂载音乐库，401 和退出清除查询缓存并卸载播放器、释放音频和画中画窗口。

后台调度、启动恢复、回收站清理及媒体维护从数据库枚举已存在用户，为每位用户建立身份上下文后执行业务操作；不借用请求用户，也不从客户端提供的任务对象选择身份。请求中断后的接收清理使用 `context.WithoutCancel` 保留原用户再加清理超时。配额、待删除文件和孤立文件扫描仍是服务实例级系统操作，维护入口显式调用，容量继续由所有账号共享。owner_user_id 与默认标签组唯一约束支持资源隔离，无需重写业务表归属；新增凭据与会话由版本化迁移补充，默认账号数据和 ID 保持不变。

任何按 ID 读取或修改资源的操作，都应同时验证资源属于当前用户。这一规则即使在初版也应执行。

## 12. 空间配额与并发

- 用户可见的已用容量是整个本地服务实例的共享容量，包括原始音频、播放副本、中间文件、候选音频版本、封面和回收站文件。
- 客户端从服务器读取权威的 `usedBytes`、`reservedBytes` 和 `limitBytes`，不得自行累加估算。
- 配额申请和释放必须具备事务性或等效的原子并发控制。
- 没有产品层面的并发任务数量限制，不代表可以绕过空间预留。
- 中断、崩溃或任务超时后，应能够识别并回收无主候选文件和过期空间预留。
- 日志和数据库文本初版不计入用户可见的 10 GiB 配额，但仍应避免无限增长。

## 13. 数据一致性原则

- 数据库中的歌曲标签关系引用稳定的歌曲 ID，而不是文件路径。
- 当前活动音频版本必须处于可播放状态。
- 删除歌曲使用软删除；文件只有在回收期届满后才能异步清理。
- 删除歌曲统一确认后软删除；标签移除与标签组删除永不删除歌曲。
- 默认标签组与无标签由系统标识，不依赖用户可编辑名称。
- 文件删除失败必须可重试和诊断，不得让数据库事务长期等待文件系统。
- 重要状态转换应记录日志，但日志不得包含完整音频内容或不必要的用户数据。

## 14. 推荐技术选型

### 14.1 总体方案

推荐采用“单体服务 + 独立前端源码 + 单进程发布”的结构：

```text
开发环境
  ├─ Go API 服务
  ├─ Vite 开发服务器
  └─ FFmpeg 子进程

发布环境
  └─ 一个 Go 服务进程
       ├─ API
       ├─ 嵌入的网页静态文件
       ├─ 音频 Range 响应
       ├─ 后台任务调度
       └─ FFmpeg / ffprobe 子进程
```

初版不使用 Docker、微服务、消息队列或独立任务工作进程。它们会增加本机安装和故障排查成本，对当前 10 GiB、默认单账号场景没有明显收益。

虽然初版不依赖 Docker，但代码和目录设计必须允许以后在 Linux 主机、NAS 或容器中运行。

### 14.2 服务器语言和 Web 框架

推荐：

- Go 1.27
- 标准库 `net/http`
- `github.com/go-chi/chi/v5` 负责轻量路由和中间件组合
- Handler + Application Service + Repository 分层，业务规则不得直接堆在 HTTP Handler 中
- 标准库 `log/slog` 输出结构化日志
- OpenAPI 描述 API 契约

选择理由：

- Go 可以为 Windows、Linux x64 和 Linux ARM64 生成独立可执行程序，适合后续 Linux 与 NAS 部署。
- 标准库可提供 HTTP、JSON、文件流、Range 响应、进程控制、嵌入静态文件和优雅关闭所需的基础能力。
- React 构建产物可以通过 `go:embed` 嵌入服务程序，生产环境只需启动一个服务进程。
- 在使用纯 Go SQLite 驱动时，可以避免 CGO 带来的跨平台编译和系统动态库依赖。
- Go 服务层通常保持较小的发布和运行开销；本项目的主要 CPU 消耗仍来自 FFmpeg，而不是 HTTP 层。

参考：[Go 支持平台与交叉编译](https://go.dev/doc/install/source#environment)、[`net/http.ServeContent`](https://pkg.go.dev/net/http#ServeContent)、[`go:embed`](https://pkg.go.dev/embed)。

Go 版本应跟随官方当前受支持版本升级。Go 官方只维护最近两个主版本，因此不应长期固定在已经退出支持的版本。

### 14.3 网页客户端和状态管理

推荐：

- React + TypeScript
- Vite
- React Router
- TanStack Query 管理服务器状态
- Zustand 管理播放器状态
- 浏览器 `sessionStorage` 持久化当前标签页的播放会话

状态边界：

| 状态类型 | 推荐位置 |
| --- | --- |
| 音乐库、标签、标签组、歌词、容量、任务状态 | TanStack Query 缓存，以服务器为权威来源 |
| 当前歌曲、播放模式、动态权重、播放器主音量 | Zustand 播放器 store |
| 刷新恢复所需的当前会话快照 | `sessionStorage` |
| 歌曲、歌词、标签与标签组等长期数据 | 服务器，不写入浏览器持久化状态 |

不要把 TanStack Query 取得的完整服务器数据再复制一份到 Zustand，避免两个状态源不同步。Zustand 只保存播放器运行状态和必要的 ID。

Vite 提供官方 React TypeScript 标签组，开发时启动快；生产构建结果通过 `go:embed` 编译进 Go 服务程序。参考：[Vite 官方入门文档](https://vite.dev/guide/)、[React TypeScript 文档](https://react.dev/learn/typescript)。

#### 14.3.1 React Native 扩展余量

初版继续使用 React DOM，不使用 React Native Web，也不要求网页 UI 组件兼容 React Native。预留工作的重点是共享非 UI 代码，而不是强行让网页与原生界面共用同一套组件。

客户端代码应按以下边界组织：

```text
apps/
  web/                    React 网页客户端
  mobile/                 未来的 React Native / Expo 客户端，初版不存在

packages/
  domain/                 歌曲、歌词、标签与标签组和播放会话类型
  api-client/             服务端 API 契约和请求封装
  player-policy/          加权随机、播放区间和队列规则
  validation/             平台无关的数据校验
```

以下代码必须保持平台无关，并允许未来由 Web 与 React Native 共同使用：

- API 请求和响应类型
- 歌曲、歌词、标签与标签组和播放会话模型
- 加权随机算法及其测试
- 播放区间、音量和下一首选择规则
- TanStack Query 的 query key 与请求函数
- Zustand 中不直接操作播放器对象的纯状态和 action
- 输入校验、错误类型和通用格式化逻辑

浏览器能力必须收敛在适配层，不得散落到共享业务代码中：

| 能力 | Web 初版实现 | 未来原生实现 |
| --- | --- | --- |
| 音频播放 | `HTMLAudioElement` | React Native 音频库 |
| 会话保存 | `sessionStorage` | 原生异步存储 |
| 文件选择 | 浏览器文件选择器 | 系统文档选择器 |
| 页面生命周期 | 浏览器事件 | React Native AppState |
| 路由 | React Router | Expo Router 或 React Navigation |

至少定义以下平台接口或等效抽象：

```text
AudioEngine
SessionStore
FilePicker
AppLifecycle
```

共享包不得直接引用 `window`、`document`、`HTMLElement`、`HTMLAudioElement`、`File`、`sessionStorage` 或其他浏览器全局对象。Web 专用代码放在 `apps/web` 或明确的 Web adapter 中。

未来增加 React Native 客户端时，预期复用共享类型、API 客户端、查询逻辑、播放器策略和状态规则；原生界面、导航、音频引擎、文件选择和本地持久化仍应按平台单独实现。

### 14.4 本地数据库和迁移

推荐：

- SQLite
- 标准库 `database/sql`
- `modernc.org/sqlite` 纯 Go SQLite 驱动
- `github.com/pressly/goose/v3` 管理嵌入式 SQL migrations
- SQLite WAL 模式
- 启用外键约束并设置合理的 busy timeout

SQLite 足以承担当前单机、小规模并发和 10 GiB 文件库对应的结构化元数据。音频文件不存入数据库，只保存文件 ID、相对路径、大小、校验值和状态。

WAL 模式允许读取和写入更好地并行，但仍只有一个写入者；这符合单机服务场景。数据库必须保存在本机磁盘，不能放在网络共享目录。参考：[SQLite WAL 官方文档](https://www.sqlite.org/wal.html)。

由于 SQLite 官方在 2026 年修复过 WAL 并发相关问题，实现时应检查纯 Go 驱动实际编译进程序的 SQLite 版本，确保为 `3.51.3` 或更高版本，或者使用包含官方回补修复的版本；不能只检查 Go module 的表面版本。

迁移策略：

1. 所有迁移文件提交到源码仓库。
2. SQL migration 使用 `go:embed` 编译进服务程序。
3. 服务启动时先检查数据库版本。
4. 有待应用 migration 时，先创建数据库备份。
5. 使用 goose 自动应用 migration；失败时停止启动并保留原数据库和错误日志。
6. SQLite 不直接支持的结构变更使用手写 SQL 完成建新表、复制数据和替换旧表。

Goose 支持 SQLite、SQL migration 和嵌入式 migration，适合把数据库升级逻辑随服务二进制一起发布。参考：[goose 项目文档](https://github.com/pressly/goose)。

### 14.5 音频探测和转码

推荐直接调用随应用分发的命令行工具：

- `ffprobe`：探测容器、编码、时长、声道、采样率和元数据，使用 JSON 输出
- `ffmpeg`：提取封面、转码和校验能否解码
- 带 `libmp3lame` 的 FFmpeg 构建：生成第 6.1 节定义的 MP3 播放副本

服务端通过受控的进程调用封装执行 FFmpeg，不使用 shell 拼接命令，不让用户输入直接成为命令参数。每个任务使用独立工作目录，并捕获退出码、标准错误、执行时间和取消信号。

Go 服务使用 `os/exec` 直接调用命令行工具，不引入 FFmpeg 语言绑定。这样更容易升级、诊断并为不同操作系统和 CPU 架构替换对应工具。`ffprobe` 原生支持机器可读输出，适合保存探测结果。参考：[ffprobe 官方文档](https://www.ffmpeg.org/ffprobe.html)、[FFmpeg libmp3lame 文档](https://www.ffmpeg.org/ffmpeg-codecs.html#libmp3lame)。

Windows x64、Linux x64 和 Linux ARM64 必须分别准备匹配架构的 FFmpeg 工具。发布前确认所选构建及启用组件的许可证，并随发布包提供所需声明。不要随意下载来源不明的可执行文件。

### 14.6 后台任务

推荐初版与 Web API 使用同一个 Go 进程：

- 后台 goroutine 负责扫描、领取和恢复任务，并由根 `context.Context` 统一取消。
- SQLite 中的 `upload_jobs` 是上传、转码和替换任务状态的权威来源。
- 当前调度器每 500 毫秒扫描持久化队列，通过条件更新领取任务，每个已领取任务使用独立 goroutine；不设置产品层面的并发数量上限，所有任务共享配额。
- FFmpeg 作为子进程执行，服务器重启时将遗留的运行中任务恢复为待处理或失败状态。
- 回收站清理、失败候选文件重试和旧版本清理由维护任务处理；SQLite 的 `pending_file_deletions` 保存旧版本及无主文件清理状态。启动时、每小时及上传/替换任务完成后触发清理。删除失败前不释放对应空间。
- 启动恢复在接受 HTTP 请求及启动工作协程之前完成：`receiving` 标记中断失败并清理；`processing` 删除未完成输出、将预留降为源文件大小并重新排队；`queued` 继续处理；`failed` 重试清理。候选文件使用确定路径，事务同时激活歌曲、更新任务成功状态并结算预留，避免崩溃造成重复入库。
- 启动时仅扫描应用托管的 `media/staging`、`media/originals`、`media/playable` 目录内常规文件；对比歌曲、任务和待删除记录，把无主文件先登记待清理并计入配额，再尝试删除。不遍历子目录或符号链接，路径比较兼容 Windows 与 Linux。
- 关闭服务时取消根 context、终止 FFmpeg 子进程，等待任务与维护 goroutine 退出后关闭 SQLite；中断的处理任务保留供下次启动恢复。

所有 goroutine 都必须有明确的所有者、退出条件和错误汇报路径。不得仅依靠内存 channel 保存任务，因为进程退出后 channel 内容会丢失。

当前不拆独立工作进程。只有出现以下情况之一时再拆分：

- FFmpeg 崩溃明显影响 Web API 稳定性。
- 需要分别限制或调度转码资源。
- 需要将任务放到另一台机器执行。
- 多账号和远程访问带来明显并发压力。

### 14.7 开发与发布

开发环境：

- `server/` 运行 `go run ./cmd/music-player`。
- `client/` 运行 Vite 开发服务器。
- Vite 将 `/api` 和音频请求代理到 Go 服务，避免开发期跨域配置扩散。
- 根目录提供 `scripts/dev.ps1` 和 `scripts/dev.sh`，分别支持 Windows PowerShell 和 Linux shell，同时启动两个开发进程并保留各自日志。
- FFmpeg 路径来自开发配置，不硬编码个人机器路径。

发布流程：

1. 前端执行固定锁文件安装和生产构建。
2. 将前端 `dist` 复制到 Go 服务的嵌入资源目录。
3. 使用 `go:embed` 将网页资源编译进服务二进制。
4. 分别构建 Windows x64、Linux x64 和 Linux ARM64 服务程序。
5. 为每个目标平台加入经过许可证检查、架构匹配的 `ffmpeg`、`ffprobe` 和声明文件。
6. 为 Windows 生成文件夹式 ZIP；为 Linux 生成 tar 包，并附带示例 `systemd` unit。

发布后只启动一个 Go 服务程序，由它同时提供网页、API 和音频。生产环境不要求安装 Go、Node.js，也不运行 Vite。网页资源嵌入服务程序，但 FFmpeg 仍作为平台相关的外部工具随包分发。

以上为完整发布目标。当前 Linux 部署使用独立的 `web/` 构建目录，显式通过 `webDir` 交给 Go 服务，FFmpeg/ffprobe 由系统软件包提供；已提供 systemd、HTTP/HTTPS Nginx 及 Let's Encrypt IP 证书续期示例，具体目录、迁移验证、备份及更新流程见 [Linux 部署与维护](linux-deployment.md)。

Linux 发布必须：

- 正确处理 `SIGTERM` 和 `SIGINT`，停止接收新请求并尽力结束或回收任务。
- 提供 `systemd` unit 示例，并设置明确的工作目录、数据目录和最低必要权限。
- 同时支持 x64 和 ARM64，避免把架构相关路径或二进制名称写死在业务代码中。
- 默认仍绑定回环地址；开放局域网访问前必须重新评估认证、反向代理和 TLS。

### 14.8 数据目录和配置

Windows 默认目录：

```text
%LOCALAPPDATA%/MusicPlayer/
  config.json
  data/
    music.db
  media/
    originals/
    playable/
    staging/
  logs/
```

Linux 系统服务默认目录：

```text
/etc/music-player/config.json
/var/lib/music-player/
  data/
    music.db
  media/
    originals/
    playable/
    staging/
```

Linux 日志默认写入标准输出和标准错误，由 `systemd-journald` 或容器日志系统收集，不强制写入 `/var/log`。开发期的非系统安装可以通过命令行参数指定用户目录。

原则：

- 用户数据不能写在应用安装或发布目录中，升级程序时不得覆盖数据。
- 数据库只保存相对于数据根目录的文件标识或相对路径。启动通过 `WithDataRoot` 为数据访问层提供绝对根目录，数据库统一写入 `media/...` 正斜杠路径；读取时解析为当前主机的绝对路径，业务服务不依赖进程工作目录。歌曲、封面、后台任务、待确认候选 JSON 和待清理文件都经过相同边界，拒绝越界路径。
- `staging` 中的临时文件必须能够在崩溃后识别和清理。
- `config.json` 保存 `addr`、`dataDir`、`database`、`webDir`、`quotaBytes`、`ffmpeg`、`ffprobe`、`logLevel`、`lrclibUrl`。完整示例见根目录 `config.example.json`；未知字段、非法 JSON、无效端口、非正配额、非法日志等级及越界数据库路径会阻止启动，不创建数据文件。
- 覆盖顺序为命令行 > 环境变量 > JSON 文件 > 平台默认。`--config` > `MUSIC_CONFIG` > 平台默认配置文件；显式文件缺失时报错，仅允许默认文件缺失时使用默认配置。各字段的环境变量和参数见 README 的配置表。配置文件中的相对路径以文件所在目录为基准，命令行和环境变量中的相对路径以启动工作目录为基准；`database` 始终相对最终数据根目录，默认 `data/music.db`。工具命令名经 `PATH` 查找，含分隔符的工具路径按上述规则解析；启动前检查工具是否可执行。日志通过 `slog` 按所选等级输出到标准输出。
- 开发启动脚本无显式配置或数据目录时，传入仓库 `.data` 以保留已有调试库；脚本透传服务器参数，FFmpeg/ffprobe 的检查由服务端按最终配置执行。直接运行二进制使用平台默认目录；不会自动把 `.data` 移入平台目录。
- 版本 12 的 Go 数据迁移在同一 SQLite 事务内转换旧路径和候选 JSON，失败回滚版本与全部路径。先在原根目录运行一次升级，再停服移动整个根目录，随后修改配置即可；不依赖原绝对路径。升级不复制或删除媒体文件，也不自动修复根目录外的记录；遇到不安全的旧路径应停止启动并保留原库。
- 初版只绑定回环地址，不默认开放局域网访问。
- 所有内部路径使用 Go 的 `path/filepath` 组合，不手写 Windows 或 Linux 路径分隔符。
- 文件标识不得依赖大小写不敏感行为；Linux 文件系统通常区分大小写。
- 数据库必须位于服务所在主机的本地文件系统或等效的本地容器卷，不得放在 SMB/NFS 网络共享上使用 WAL。音乐文件可以位于单独的数据卷，但需要稳定的文件锁、原子重命名和权限语义。

### 14.9 备份与恢复

初版推荐冷备份，保持实现简单和结果可靠：

1. 停止服务。
2. Windows 运行 `scripts/backup.ps1`，Linux 运行 `scripts/backup.sh`；脚本接收明确的数据目录，将其复制到用户选择的外部目录，并生成时间戳和清单文件。
3. 音频通常已经压缩，默认不再打 ZIP，以减少时间和临时空间占用。
4. 恢复时停止服务，验证清单后用备份目录替换数据目录，再启动服务并执行版本检查。

备份脚本检测到服务仍在运行时应拒绝直接复制，避免遗漏 WAL 内容或复制到不一致状态。脚本不得假设固定 Windows 盘符或 Linux 用户名。以后如果需要不停机备份，再使用 SQLite Online Backup API 创建一致的数据库快照，并为备份期间引用的媒体文件增加保护。参考：[SQLite Online Backup API](https://www.sqlite.org/backup.html)。

### 14.11 封面派生文件

使用 ffprobe 的 `attached_pic` 标记选择第一张内嵌图片，由 FFmpeg 输出等比缩放、最长边 512 像素、质量参数 `-q:v 4` 的 JPEG。不将普通视频帧当作封面，也不依赖浏览器解码上传文件里的图片格式。派生文件写入前预留容量，最终大小计入歌曲总容量。

迁移 `011_track_covers.sql` 增加 `cover_path` 与 `cover_scan_version`。上传和音频替换在原有任务中处理封面，原子提交歌曲、音频和封面引用。旧记录通过内部 `cover` 持久化任务补提取，启动和定期维护时调度；处理中重启会清除候选图片、释放任务预留后重排队，失败清理不得删除原音频。完成时检查用户、源文件版本及任务预留，避免将旧版本图片关联到替换后的音频。未发现封面也记录已扫描，避免重复扫描。

`GET /api/tracks/{trackID}/cover` 校验当前用户及歌曲有效状态，以 `image/jpeg` 返回图片；客户端使用带音频版本的 `coverUrl` 缓存，替换后更新地址。内部封面任务不展示在上传列表中，客户端仍跟踪其结束以刷新歌曲数据。封面路径使用服务器生成的标识，纳入候选文件恢复、替换清理、回收站与容量统计。
### 14.12 用户替换封面

歌曲设置将“替换封面”和“替换音频”并排显示为相同风格的直接选文件按钮，不增加折叠或二级入口。封面提供本地图片选择，预览直接替换按钮内的原封面缩略图，不增加单独的预览行；封面和音频文件都仅暂存为设置草稿，由底部“保存”统一发送，取消丢弃草稿；预览使用 Web 适配层的对象 URL，并在更换文件或关闭设置后释放。支持 JPG、PNG、WebP、GIF、BMP，单图最多 8 MiB；保留既有图片类型、解码、32 Mi 像素上限与 JPEG 归一化校验。结果仍为最长边 512 像素的 JPEG。替换封面只增加 cover_version，封面地址使用 `?v={audioVersion}&c={coverVersion}`，不改变音频版本或播放进度。

`POST /api/tracks/{id}/cover` 改为 multipart 文件上传，先校验歌曲所有权，使用生成的任务 ID 存入 staging，每次写盘前原子预留容量。完整接收并同步到磁盘后，转为内部 kind=cover 后台任务；客户端通过歌曲设置的统一保存流程显示状态并轮询至终态，内部任务不进入上传列表。图片选择或取消不发送请求；失败保留原封面并支持重新选择或重试。

统一保存先校验并保存歌曲设置，再等待所选音频替换完成，最后执行封面替换，避免音频内嵌封面覆盖用户选择。仅全部完成后关闭窗口，期间禁用编辑、取消与重复提交；成功步骤清除对应文件草稿，失败保留未完成部分。各接口不组成跨请求事务，部分成功时明确提示，取消不回滚已完成步骤。查询已接收任务失败时保留任务 ID，重试优先继续查询，避免重复上传；任务明确失败后才允许重新提交同一文件。已完整接收的任务继续沿用服务器重启恢复流程；未提交文件不写入浏览器会话存储。

迁移 `014_cover_upload.sql` 增加任务 cover_input_path，结束旧的未完成在线任务并移除 cover_release_id。在线搜索、预览代理和外部服务客户端一并移除，既有封面文件不变。旧任务的候选文件和预留由既有失败清理回收，不能删除其 source_path 指向的歌曲原文件；迁移 013 作为历史迁移保留。

任务保留歌曲原路径用于版本校验，cover_input_path 独立记录上传图片，数据库路径仍相对数据根目录。转换过程不删除上传输入，事务同时更新封面和容量、清零任务预留、将上传输入和旧封面加入待清理队列；输入文件在待清理完成前仍计入已用空间。处理中断后删除不完整 JPEG，保留已完整上传的输入，以输入实际大小恢复预留并重新排队；接收中断或输入缺失则失败并清理。后台转换完成与文件清理之间崩溃时，由持久化队列继续清理。
